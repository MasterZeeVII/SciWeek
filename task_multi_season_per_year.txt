TASK: allow more than one tournament per calendar year (e.g. 2026 #1 and 2026 #2)
================================================================================
Status: DESIGN APPROVED — ready to implement. Read CLAUDE.md at repo root first,
especially "The database owns the schema" (there are NO Django migrations; the
DB + sciweek.sql change first, models mirror it second, never run makemigrations).

WHY (context for whoever picks this up)
---------------------------------------
Question raised in review: "can it create 2 tournaments in the same year?"
Answer today: NO, and it fails silently rather than erroring. Two separate
brackets in one year is a real scenario (a second, independent event in the
same calendar year — different teams/schools, not a second stage of the same
event, so modelling it as an extra Division or Round group is NOT appropriate).

Current hard constraints, all three layers:
  - sciweek.sql:67   `UNIQUE KEY \`uq_year\` (\`year\`)` on `tournaments`
  - src/common/models.py:53  `year = models.PositiveSmallIntegerField(unique=True)`
  - src/service/tournament.py:17-27  `upsert_tournament()` does
    `Tournament.objects.get_or_create(year=year)` then overwrites `.name`.

The silent-failure path: POST /api/tournaments/ with name "SCIWEEK #2", year
2026 when a 2026 season already exists does NOT create a second tournament and
does NOT error — it RENAMES the existing 2026 season and re-activates it. The
admin UI even documents this behaviour in Thai at
frontend/src/admin/pages/admin-tournaments.tsx:131-134. Losing the name of a
live season by typing the wrong year is the actual bug here, so fixing this is
worth doing even beyond the multi-season requirement.

DESIGN
------
Add a `season` discriminator column to `tournaments`; identity becomes the pair
(year, season). Existing rows backfill to season = 1. Do NOT drop `year` and do
NOT encode the sequence into `name` — `year` is load-bearing for sorting, the
season badges, and the dashboard "hall of fame" aggregates.

Rejected alternative: bump the year (2026 -> 2027) for the second event. It
breaks every year-derived display and the cross-season stats. Don't.

STEP 1 — DATABASE (do this FIRST, before touching Python)
---------------------------------------------------------
Run against the live MySQL/MariaDB DB (DB_* in .env, defaults to 192.168.1.37):

    ALTER TABLE `tournaments`
      ADD COLUMN `season` smallint unsigned NOT NULL DEFAULT 1 AFTER `year`,
      DROP INDEX `uq_year`,
      ADD UNIQUE KEY `uq_year_season` (`year`,`season`);

Existing rows pick up season = 1 from the DEFAULT — no separate backfill needed.
Verify before/after with `SELECT id, name, year, season, is_active FROM tournaments;`

Then hand-edit sciweek.sql (the checked-in source of truth) so lines 60-68 match:
the new `season` column and `uq_year_season` replacing `uq_year`. Keep the file a
valid phpMyAdmin-style dump — same formatting/quoting style as its neighbours.

STEP 2 — MODEL (src/common/models.py:50-62)
-------------------------------------------
  - `year`: DROP `unique=True` (it is now only unique in combination).
  - ADD `season = models.PositiveSmallIntegerField(default=1)`.
  - Meta: add `constraints = [models.UniqueConstraint(fields=["year", "season"],
    name="uq_year_season")]` to mirror the DB, and change
    `ordering = ["-year"]` -> `ordering = ["-year", "-season"]`.
  - `__str__`: `f"{self.name} {self.year}"` -> include season when > 1.

Do NOT run makemigrations. `manage.py check` should still pass.

STEP 3 — SERVICE (src/service/tournament.py:17-27)
--------------------------------------------------
`upsert_tournament(name, year)` -> `upsert_tournament(name, year, season=1)`,
with `get_or_create(year=year, season=season, defaults={"name": name})`.

Keep it an upsert, just keyed on the pair — the UI's documented "same season
again = rename + reactivate" behaviour stays true, it is simply no longer
triggered by an unrelated second event in the same year.

ALSO ADD `next_season_for_year(year)` returning
`(max season for that year) + 1`, or 1 if the year is unused. The frontend needs
this to prefill the field so staff never have to guess an unused number (see
step 6). Put it in this module next to upsert_tournament.

STEP 4 — SERIALIZERS (src/api/serializers.py)
---------------------------------------------
The display name `f"{tournament.name} {tournament.year}"` is duplicated at THREE
call sites — do not add a fourth copy of the format string:
    - :365  public_tournaments_payload()   (public season list)
    - :467  public_tournament_payload()    (public season detail)
    - :504  state_payload()                (every admin mutation response)

Add ONE module-level helper, e.g.:

    def tournament_display_name(tournament):
        """Season 1 keeps the historical bare "<name> <year>" label so existing
        seasons render exactly as before; only a second+ season in the same year
        gets the disambiguating suffix."""
        base = f"{tournament.name} {tournament.year}"
        return base if tournament.season <= 1 else f"{base} (#{tournament.season})"

Point all three sites at it. Also add `"season": tournament.season` to all three
payloads next to the existing `"year"` key (frontend needs it for badges).

Ordering: `Tournament.objects.order_by("-year")` at :352 ->
`order_by("-year", "-season")` so the newest season of a year sorts first.

dashboard_stats_payload() (:375-429) — CAREFUL, this one has real logic to fix.
It treats the YEAR as the season identity:
    - `all_years` (:399, :403) and `total_seasons = len(all_years)` (:411)
    - `years_by_school` (:400, :409) and the per-school `len(years)` title count
    - `"everySeason": total_seasons > 0 and len(years) == total_seasons` (:417)
With two tournaments in 2026, a set of years silently collapses them into one,
so `totalSeasons` undercounts and a school that won both 2026 events is credited
with a single title. Change the set/dict keys from `tournament.year` to the
`(year, season)` tuple, keep `len()` for the counts, and when emitting
`"years": sorted(years)` (:416) map the tuples back to display strings via the
same helper convention as step 4 (e.g. "2026" / "2026 (#2)") — the frontend
renders that array verbatim with `.join(", ")` at
frontend/src/admin/pages/admin-dashboard.tsx:227, so a tuple leaking into JSON
would render as garbage. Update the HallOfFameEntry type accordingly (step 6).
